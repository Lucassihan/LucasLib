Implementation · every step

The Pipeline

This is the whole filter, in execution order, with the real code and the reason every line exists — down to how a single distance reading is grabbed and why heading is read in degrees but used in radians. If you read this top to bottom you will understand exactly what happens to your robot's pose 50 times a second.

Two threads, one shared pose

Two tasks run concurrently. odometryTask (~100 Hz) updates chassis from the encoders/IMU and stashes the motion. mclTask (~50 Hz) reads that motion, runs the filter, and nudges chassis back toward the walls. On the V5 these are time-sliced on one core — the split buys responsiveness (odometry stays fast while the filter grinds), not extra speed.

Step 0 — Setup and the loop skeleton

StartMCL(x, y) does two things, once: it builds the 4 distance-sensor models from the config + the real devices, and it seeds the particle cloud around the known starting pose. Until you call it, mclTask idles.

static ParticleFilter    mcl;
static MCLDistanceSensor sensorObjects[4];
static bool mclInitialized = false, mclReady = false;

void StartMCL(double startX, double startY) {
  initSensorsOnce();          // configure 4 sensors from MCLConfig + DistSensor1..4, register them
  mcl.seedAround(startX, startY);
  mclReady = true;
}mcl.cpp

seedAround scatters all 400 particles in a small SEED_STD (1.5 in) blob around the start — a tight cloud, because you know roughly where the robot begins an autonomous routine.

void seedAround(double centerX, double centerY) {
  for (int i = 0; i < N; i++) {
    particles[i].x = centerX + randomBetween(-MCLConfig.SEED_STD, MCLConfig.SEED_STD);
    particles[i].y = centerY + randomBetween(-MCLConfig.SEED_STD, MCLConfig.SEED_STD);
  }
  estimate.x = centerX; estimate.y = centerY;
}mcl.h · ParticleFilter
Small detail · a particle

A particle is just struct Particle { double x = 0, y = 0; } — position only, no heading. Heading is shared from the IMU for every particle, so the filter only ever solves for (x, y). That's the single biggest simplification, and it's deliberate (see Predict).

Step 1 — Where the motion comes from (odometry side)

The filter never reads encoders itself. It reuses the motion track() already computes every odometry cycle. LucasLib's track() does arc-chord integration (constant-curvature over the cycle) to get a local displacement, rotates it into the field frame, and adds it to chassis.x/y. We tap that exact global delta:

// inside Odometry::track(), where x/y are updated:
double avgHRad = h * (M_PI / 180.0) + dhRad / 2.0;       // average heading over the cycle
double gdx = localDY * sin(avgHRad) + localDX * cos(avgHRad);
double gdy = localDY * cos(avgHRad) - localDX * sin(avgHRad);

mclMutex.lock();
x += gdx;
y += gdy;
mclAccumDX += gdx;   // <-- accumulate the SAME global delta for the MCL task
mclAccumDY += gdy;
mclMutex.unlock();odometry.cpp · track()
Why accumulate in the GLOBAL frame

Odometry runs faster than the filter, so between MCL cycles many track() calls happen. We sum the global (field-frame) deltas, not local ones — because across a turn the local frame rotates, so summing local deltas would be wrong, but global deltas add cleanly. And because every particle shares the IMU heading, that one global delta is the correct motion for all particles.

Why the mutex

Two threads touch chassis.x/y and the accumulator: track() writes them, mclTask reads/zeros the accumulator and blends into x/y. A double isn't written atomically on the V5, so without mclMutex a reader could catch a half-updated value. The lock is held for just a few assignments, so it's effectively free.

Step 2 — Consuming the motion (filter side)

Each cycle mclTask grabs the accumulated motion and zeroes it (so the next cycle only sees new motion), then gathers the heading and the slip estimate:

chassis.mclMutex.lock();
double globalDX = chassis.mclAccumDX;
double globalDY = chassis.mclAccumDY;
chassis.mclAccumDX = 0;          // reset: we've now "spent" this motion
chassis.mclAccumDY = 0;
chassis.mclMutex.unlock();

double headingRad = TO_RAD(chassis.h);                                   // IMU heading: deg -> rad (util.h)
double slipAccel  = centripetalAcceleration(chassis.velocity, chassis.travelArcRadius());
mcl.step(globalDX, globalDY, headingRad, slipAccel, vex::timer::system());mcl.cpp · mclTask()
Small detail · degrees in, radians used

chassis.h is in degrees, VEX convention (0° = +Y / downfield, clockwise positive). Every trig call inside the filter needs radians, so we convert once here. Get this wrong and the ray-cast points the wrong way — the #1 cause of a confidently-wrong filter.

Small detail · the slip number

chassis.velocity and chassis.travelArcRadius() are already computed by track(). centripetalAcceleration() turns them into v²/r — how hard the robot is being flung sideways right now. It feeds the sideways noise in Predict (a hard turn at speed is likely slipping, so spread more). Straight driving → huge radius → ~0.

From here we're inside ParticleFilter::step(), which runs the rest in order:

void step(double globalDX, double globalDY, double headingRad, double slipAccel, uint32_t nowMs) {
  injectRandomParticles();                              // 3a (off by default)
  moveEveryParticle(globalDX, globalDY, headingRad, slipAccel);  // 3b PREDICT
  distanceSinceUpdate += sqrt(globalDX*globalDX + globalDY*globalDY);

  // 4 GATE
  double secondsSinceUpdate = double(nowMs - lastUpdateMs) / 1000.0;
  bool movedEnough  = distanceSinceUpdate >= MCLConfig.MIN_UPDATE_DIST;
  bool waitedEnough = secondsSinceUpdate >= MCLConfig.MAX_NO_UPDATE_TIME;
  if (!movedEnough && !waitedEnough) { updateEstimate(); return; }
  if (sensorCount == 0)              { updateEstimate(); return; }

  readEverySensorOnce();                                // 5
  double totalWeight = weightEveryParticle(headingRad); // 6
  if (totalWeight <= 0.0) { updateEstimate(); return; }

  resample();                                           // 7
  updateEstimate();                                     // 8
  distanceSinceUpdate = 0.0; lastUpdateMs = nowMs;
}mcl.h · ParticleFilter::step()

Step 3 — Predict (move every particle)

We push every particle by the robot's motion, then add a little noise to each so the cloud covers many "what really happened" possibilities. The noise is bigger sideways than forward (this robot has a forward tracker but no sideways one), and grows further when the robot is likely slipping.

void moveEveryParticle(double globalDX, double globalDY, double headingRad, double slipAccel) {
  double distanceMoved = sqrt(globalDX*globalDX + globalDY*globalDY);

  // friction holds up to maxLateralAccel(); only the EXCESS makes the robot actually slide
  double excessAccel = slipAccel - MCLConfig.maxLateralAccel();
  if (excessAccel < 0.0) { excessAccel = 0.0; }
  double sidewaysFraction = MCLConfig.SIDEWAYS_NOISE + MCLConfig.SLIP_GAIN * excessAccel;

  for (int i = 0; i < N; i++) {
    // 1. noise in the ROBOT's own frame
    double forwardNoise  = randomBetween(-1,1) * MCLConfig.FORWARD_NOISE * distanceMoved;
    double sidewaysNoise = randomBetween(-1,1) * sidewaysFraction        * distanceMoved;

    // 2. rotate that robot-frame noise into field X/Y
    double noiseX = forwardNoise * sin(headingRad) + sidewaysNoise * cos(headingRad);
    double noiseY = forwardNoise * cos(headingRad) - sidewaysNoise * sin(headingRad);

    // 3. move: the real motion + this particle's own noise
    particles[i].x += globalDX + noiseX;
    particles[i].y += globalDY + noiseY;

    clampToField(particles[i]);     // a robot can't be outside the walls
  }
}mcl.h
Why add noise to clean inputs

It feels wrong to dirty a known motion, but with 400 particles those small, independent jitters become a spread of hypotheses. The update step thrives on that spread — it's how the filter rules out wrong areas. No noise → the cloud is a single point that can never re-estimate anything.

Why sideways > forward, and the slip term

With no lateral tracker, sideways motion is the unmeasured axis, so we're less sure of it → bigger base noise (SIDEWAYS_NOISE). And when v²/r exceeds the measured friction limit maxLateralAccel(), the robot is genuinely sliding, so the extra term widens the sideways spread exactly then. The same maxLateralAccel() is what boomerang can use to cap speed.

Why clamp to the field

The robot physically cannot be outside the perimeter, so neither can a valid hypothesis. Clamping keeps every particle inside ±70.4 in. (An earlier version teleported out-of-field particles to random spots instead — that hijacked the estimate; see the Testing Chronicle.)

Step 4 — The update gate (don't resample too often)

The expensive part (weighting + resampling) only runs once the robot has actually moved MIN_UPDATE_DIST (2 in) or MAX_NO_UPDATE_TIME (2 s) has passed. Otherwise we just refresh the estimate and return.

Why gate

If you resample every cycle while the robot sits still, the cloud keeps collapsing onto the best few particles and loses all its spread — so the moment the robot moves again, it has no diversity to track with. Gating on distance moved keeps the cloud healthy: you only fold in a new measurement when there's genuinely new information.

Step 5 — Reading the distance sensors (once each)

Here is exactly how a reading is grabbed. readEverySensorOnce() calls update() on each sensor one time per cycle; that value is then reused for all 400 particles.

void readEverySensorOnce() {
  for (int s = 0; s < sensorCount; s++) { sensors[s]->update(); }
}mcl.h
void update() override {
  hasValidReading = device->isObjectDetected();                       // is anything in range?
  double rawMillimeters = device->objectDistance(vex::distanceUnits::mm); // grab the reading, in mm
  measuredInches = scaleConstant * rawMillimeters / 25.4;             // mm -> in, with per-sensor fix

  if (measuredInches > MCLConfig.SENSOR_MAX_RANGE) {                  // too far to trust?
    hasValidReading = false;
  }

  standardDeviation = MCLConfig.SENSOR_STD_FRAC * measuredInches;     // 2.5% of the reading
  if (standardDeviation < MCLConfig.SENSOR_STD_FLOOR) {               // never tighter than the floor
    standardDeviation = MCLConfig.SENSOR_STD_FLOOR;
  }
}mcl.h · MCLDistanceSensor
Small detail · how the reading is grabbed, line by line

① device->isObjectDetected() — VEXcode bool, false if nothing's in range. ② device->objectDistance(distanceUnits::mm) — the raw distance, in millimetres (VEXcode's native unit for this call). ③ multiply by the per-sensor scaleConstant (each sensor reads ~1–3% high) and divide by 25.4 to get inches. ④ if it's past SENSOR_MAX_RANGE (78 in) we mark it invalid — beyond ~2 m the V5 sensor is junk. ⑤ the standard deviation is 2.5% of the reading (the datasheet's accuracy), floored at 0.5 in.

Why ONCE per cycle

400 particles × 4 sensors = 1,600 ray-casts per cycle. If each ray-cast re-queried the hardware that'd be 1,600 device reads — it would bog the brain. So we read each sensor once into measuredInches/standardDeviation and reuse those numbers for every particle. VEXcode has no confidence accessor (PROS does, 0–63), so we don't have a per-reading quality value — the range gate + fixed σ stand in for it.

Why we don't gate on objectSize()

VEXcode's objectSize() is an enum (none/small/medium/large) and it changes between foam practice fields and metal competition fields, so it's unreliable as a validity signal. We rely on isObjectDetected() + the range cap instead.

Step 6 — Weighting (how well each particle agrees)

Every particle's weight is the product of each sensor's vote: "if the robot were at this particle, how likely is the reading I just took?"

double weightEveryParticle(double headingRad) {
  double totalWeight = 0.0;
  for (int i = 0; i < N; i++) {
    double weight = 1.0;
    for (int s = 0; s < sensorCount; s++) {
      SensorVote vote = sensors[s]->p(particles[i].x, particles[i].y, headingRad);
      if (vote.valid) { weight = weight * vote.weight; }   // abstaining sensors skipped
    }
    weights[i] = weight;
    totalWeight += weight;
  }
  return totalWeight;
}mcl.h

The vote itself — this is where the field geometry enters. The sensor's mount is rotated into the field by the particle's pose, a ray is cast to the nearest wall, and the expected distance is scored against the actual reading with a bell curve:

SensorVote p(double px, double py, double headingRad) override {
  if (!hasValidReading) { return { false, 0.0 }; }    // abstain: this sensor sits out the vote

  // 1. sensor's position in the field (rotate the robot-frame mount by heading)
  double sensorX = px + mountForward * sin(headingRad) + mountSideways * cos(headingRad);
  double sensorY = py + mountForward * cos(headingRad) - mountSideways * sin(headingRad);
  // 2. which way it points in the field
  double sensorHeadingRad = headingRad + mountAngleRad;   // mount angle pre-converted at setup
  // 3. how far it SHOULD read to a wall from there
  double expectedInches = rayToWalls(sensorX, sensorY, sensorHeadingRad);
  // 4. score the match, with a floor so one bad reading can't zero a good particle
  double score = bellCurve(expectedInches, measuredInches, standardDeviation);
  if (score < MCLConfig.HEAVY_TAIL_FLOOR) { score = MCLConfig.HEAVY_TAIL_FLOOR; }
  return { true, score * MCLConfig.DISTANCE_WEIGHT };
}mcl.h · MCLDistanceSensor::p()

The ray-cast is the heart of the measurement model — "from this point, looking this way, how far is the nearest wall?"

inline double rayToWalls(double sx, double sy, double phiRad) {
  const double H = MCLConfig.FIELD_HALF;
  double dx = sin(phiRad), dy = cos(phiRad);    // VEX convention: heading 0 = +Y
  double best = MCLConfig.SENSOR_MAX_RANGE;
  if (dx >  1e-9) { double t = ( H - sx)/dx; if (t>0 && fabs(sy+t*dy)<=H) best=fmin(best,t); }
  if (dx < -1e-9) { double t = (-H - sx)/dx; if (t>0 && fabs(sy+t*dy)<=H) best=fmin(best,t); }
  if (dy >  1e-9) { double t = ( H - sy)/dy; if (t>0 && fabs(sx+t*dx)<=H) best=fmin(best,t); }
  if (dy < -1e-9) { double t = (-H - sy)/dy; if (t>0 && fabs(sx+t*dx)<=H) best=fmin(best,t); }
  return best;
}mcl.h
Small detail · the convention, baked in

A ray at VEX heading phi travels in direction (sin phi, cos phi) — that's the same mapping track() uses (forward maps to (sin, cos)). For each of the 4 walls (x = ±H, y = ±H) we solve for the distance t along the ray, keep it only if the hit lands on the actual finite wall segment (fabs(...) <= H), and take the nearest. Capped at SENSOR_MAX_RANGE.

Why the heavy-tail floor

A pure bell curve drops to ~0 for a big mismatch, so a single bad reading (an opponent in the beam, or a wall just out of range) could zero a particle's whole weight even if it's right about everything else. Flooring each vote at HEAVY_TAIL_FLOOR (0.05) means one wild sensor only knocks a particle down ~20×, not to zero — the other sensors still get a say. This was added after testing; without it the cloud collapsed near walls.

Why a SensorVote (not std::optional)

A sensor with nothing in range returns { false, 0.0 } (abstain) and is simply skipped in the product — it neither helps nor hurts. This is how the filter copes when a sensor faces across the field and sees nothing within 78 in. We use a tiny struct SensorVote { bool valid; double weight; } rather than std::optional because the VEX toolchain's libstdc++ (GCC 4.9) predates the C++17 <optional> header.

Step 7 — Resample (survival of the fittest) + roughening

Resampling rebuilds the cloud, copying heavy particles often and dropping light ones, so the population concentrates where the weight is. We use systematic resampling: lay all the weights end-to-end, drop N evenly-spaced points, keep whichever particle each lands on.

void resample() {
  double totalWeight = 0.0;
  for (int i = 0; i < N; i++) { totalWeight += weights[i]; }
  double spacing = totalWeight / double(N);
  double firstPoint = randomBetween(0.0, spacing);     // one random offset
  for (int i = 0; i < N; i++) { oldParticles[i] = particles[i]; }

  int sourceIndex = 0; double weightSoFar = weights[0];
  for (int newIndex = 0; newIndex < N; newIndex++) {
    double thisPoint = firstPoint + double(newIndex) * spacing;
    while (thisPoint > weightSoFar && sourceIndex < N - 1) {
      sourceIndex++; weightSoFar += weights[sourceIndex];
    }
    // copy the chosen particle, then ROUGHEN it so duplicates don't stack on one point
    particles[newIndex].x = oldParticles[sourceIndex].x + randomBetween(-1,1) * MCLConfig.ROUGHEN_STD;
    particles[newIndex].y = oldParticles[sourceIndex].y + randomBetween(-1,1) * MCLConfig.ROUGHEN_STD;
    clampToField(particles[newIndex]);
  }
}mcl.h
Why systematic (not plain random)

Drawing N independent random picks can, by luck, over-sample one heavy particle and throw away diversity. Systematic resampling uses a single random offset then evenly-spaced picks — lowest variance, O(N), one random number. A heavy particle simply spans more comb points, so it's copied proportionally.

Why roughening

Resampling copies particles, so without roughening, heavy particles become many identical points — the cloud collapses to a few exact locations and loses its ability to re-estimate. Adding a little jitter (ROUGHEN_STD = 0.4 in) after each copy keeps the cloud a healthy spread. This is also what lets it diffuse back to the truth after a shove (see Testing).

Step 8 — The estimate (where do we think we are?)

void updateEstimate() {
  double sumX = 0, sumY = 0;
  for (int i = 0; i < N; i++) { sumX += particles[i].x; sumY += particles[i].y; }
  estimate.x = sumX / double(N);
  estimate.y = sumY / double(N);
}mcl.h
Why a plain mean is correct here

Right after resampling, every particle carries equal weight (the weights are "spent"), so the plain average is the proper estimate of the cloud's center. On gate-closed cycles the cloud is still equal-weighted from the last resample and only shifted by Predict, so the plain mean stays correct there too. (The crowd's average beats its single best member.)

Step 9 — Blend into chassis (the payoff)

Back in mclTask, we nudge the canonical pose a fraction of the way toward the estimate — we never snap, and we never touch heading.

chassis.mclMutex.lock();
chassis.x += MCLConfig.MCL_WEIGHT * (mcl.estimate.x - chassis.x);   // 35% of the way
chassis.y += MCLConfig.MCL_WEIGHT * (mcl.estimate.y - chassis.y);
chassis.mclMutex.unlock();
// chassis.h is NEVER touched -- resolveHeading owns heading.mcl.cpp
Why blend, and why into the live pose

Snapping the pose straight to the estimate would jitter the robot and let one bad cycle teleport it — so we move only 35% per cycle (a low-pass filter on the correction; a fixed-gain complementary filter). And we add the correction into the same chassis.x/y that odometry keeps updating, rather than averaging against a separate free-running odometry pose. That increment-based blend means drift can never accumulate in the output: each cycle odometry adds a little, MCL trims a little.

The result

chassis.x/y/h is now odometry-smooth moment-to-moment and re-anchored to the walls a few times a second. Your driveTo, boomerang, and pure-pursuit code reads it exactly as before — they just ride a pose that self-corrects instead of one that only drifts.
