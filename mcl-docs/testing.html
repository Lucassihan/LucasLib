Testing Chronicle

The filter did not work the first time — or the second, or the third. This is the honest record of every failure, what caused it, and the fix, because the bugs are the design rationale: each robustness feature in the code exists because a specific test broke without it. All results are from off-robot simulation (it has not yet run on hardware).

The test harness

There's no VEX SDK off the robot, so the real mcl.h + mclConfig.cpp are compiled with clang++ against a tiny stub vex.h — a programmable vex::distance (you set what it reads), a no-op mutex, a fake timer. Then a simulated robot drives a path while we generate the sensor readings from the true pose:

// each step: feed the filter the true motion + sensor readings, then measure error
double td = rayToWalls(trueSensorX, trueSensorY, trueSensorAngle);  // what the wall really is
device._mm = (td + noise) * 25.4;                                   // what the sensor "reads"
pf.step(globalDX, globalDY, headingRad, slipAccel, nowMs);
double error = hypot(pf.estimate.x - truth.x, pf.estimate.y - truth.y);test harness (off-robot)

This exercises the real filter code end-to-end — the same ray-cast, weighting, and resampling that run on the robot. Two scenarios matter: a standalone filter (estimate vs. truth, the harshest test) and the faithful integration (odometry + 35% blend, measuring the blended chassis pose — what actually ships).

First good sign

From the very first run the filter tracked beautifully when well-observed — 0.1–0.5 in error in the open field. So the core math (ray-cast, convention, weighting) was right early. Every bug below was about robustness, not correctness.

Bug 1 — Particle impoverishment (the cloud collapses)

Symptom. The standalone filter tracked at 0.1–0.5 in, then suffered episodes of ~11 in error (avg 10.67), always near a wall. A stationary test was damning: seeded at (10,10) with truth at (0,0), the estimate never moved from the seed — stuck at 14.2 in error for 30 cycles.

Diagnosis. With a tight σ the bell-curve likelihood is razor-peaked, so the single particle closest to truth gets almost all the weight and resampling copies it 400 times — the cloud collapses to one point with zero diversity. Once collapsed, if a constraining sensor saturates near a wall, there's nothing left to re-spread and re-estimate, so it drifts. (The static test also showed the flip side: with no particle near truth and no motion, there's nothing to select — you can't find what you never sampled.)

Fix. Three things, now core: roughening (jitter each particle after resampling so duplicates don't stack), a σ floor (SENSOR_STD_FLOOR, stop the likelihood getting razor-thin), and the heavy-tail floor (a far-off reading can't drive weight to exactly zero).

Bug 2 — The out-of-field reinit hijack

Symptom. Sudden 81-inch jumps: at one step the estimate teleported clear across the field (truth x = 22, estimate x = −60), then clawed back.

Diagnosis. The first version handled particles that wandered off the field by teleporting them to a random spot anywhere on the field. Near a wall, where only one or two sensors are in range, those random particles could happen to match the few valid readings and get high weight — hijacking the estimate to a random location.

Fix. Stop teleporting. A robot physically can't leave the field, so a valid hypothesis can't either — clamp every particle to ±70.4 in in Predict (and after roughening). Particles stay local; no random hijack. (Ironically, removing this destructive reinit exposed the next bug — it had been doubling as a crude recovery mechanism.)

Bug 3 — Deprivation after a low-observability moment

Symptom. After the clamp fix, a new failure: the moment the robot passed through a pose where only one sensor was in range, the cloud drifted ~28 in and then sat at a constant 28-inch offset that never recovered (avg 26.2), even when all sensors came back.

Diagnosis. During the one-sensor moment the under-constrained axis drifted. With the cloud now tightly clamped and roughened only ±0.4 in, no particle spanned the 28-inch gap to the truth — so when observability returned, there was nothing near the right answer to select. Classic particle deprivation. (The old random reinit had accidentally been the cure, by scattering particles everywhere.)

Attempted fix. Augmented MCL — inject a small fraction (2%) of fresh random particles every step, so the filter can rediscover a pose it had ruled out. This led straight to Bug 4.

Bug 4 — Injection biases unobserved axes

Symptom. Injection made things worse. In a shove test (an 8-inch push the odometry misses), INJECT_FRAC = 0.02 spiked the error to 33 in mid-recovery before settling — while INJECT_FRAC = 0 recovered cleanly and monotonically.

Diagnosis. Injected particles are spread uniformly across the field, so their average sits at field-center. On an axis the sensors can't currently observe, those injected particles aren't pruned, so they drag the estimate's mean toward the center of the field — a systematic bias exactly where you have the least information. Worse, the 35% blend then feeds that biased estimate into the otherwise-good odometry value.

Fix. INJECT_FRAC = 0 by default. For tracking from a known autonomous start (the VEX case) you never need global re-discovery, and roughening already provides enough diffusion to recover from a bump. Injection stays as an opt-in knob for teams who specifically want kidnap recovery and can tolerate the bias.

The real lesson — the standalone test was lying

The wall-hugging, fast-rotating path in the standalone test creates a genuinely hard situation: with 4 sensors at 90° spacing, near a wall the in-range sensors often all see the same wall, leaving one axis momentarily unobservable. At one step both valid sensors saw the right wall → x was perfect (55.1 vs 55) and y drifted 45 in. That is not a bug — the filter can't observe what the sensors don't see.

Why the real robot is fine where the test wasn't

The standalone test measured the filter alone, with no odometry holding the unobserved axis. On the real robot, odometry keeps writing chassis.x/y and MCL only nudges it 35%; an axis MCL can't see is held steady by odometry until a sensor can correct it. The fix for the test was to stop testing a fiction and test the actual system: odometry + blend.

What's NOT yet tested

This is all simulation. It has not run on a real robot. Real-world unknowns the sim can't capture: actual sensor noise/beam behaviour, IMU drift, opponents in the beam, field-tolerance variation, and whether your measured mounts/scale/slip-force are right. Treat the bring-up order as mandatory before trusting it in a match.
