Config & Tuning

Every knob lives in one struct, MCLConfig, with the numbers set in src/mcl/mclConfig.cpp. Read it with a dot: MCLConfig.MCL_WEIGHT, MCLConfig.maxLateralAccel(). This page explains each field and, crucially, sorts them into measure (physical facts about your robot), tune (behaviour dials), and leave alone.

How the config is structured

It's a plain struct with one global instance. Two constants are compile-time (static constexpr, used to size the particle array); everything else is a runtime field you can even change live from a tuner.

struct MclConfig {
  static constexpr int    NUM_PARTICLES = 400;     // array size (compile-time)
  static constexpr double FIELD_HALF    = 70.4375; // inches, center to a wall
  double FORWARD_NOISE, SIDEWAYS_NOISE, ... ;      // runtime knobs
  double SENSOR_FORWARD[4], ... ;                  // per-sensor mounts
  double SIDE_PUSH_FORCE, ROBOT_WEIGHT;            // slip physics
  double maxLateralAccel() const { return (SIDE_PUSH_FORCE / ROBOT_WEIGHT) * 39.3701; }
};
extern MclConfig MCLConfig;                        // the one instance (values in mclConfig.cpp)mclConfig.h

Things you MEASURE (physical facts — get these right first)

These describe your actual robot. They are not "tuned" — they're measured, and a wrong value here makes the filter confidently wrong.

FieldUnitsWhat it is & how to get it
SENSOR_FORWARD[4]inHow far ahead of the tracking center each sensor sits (a back-facing sensor is negative). Measure with a ruler / from CAD. Index matches DistSensor1..4.
SENSOR_SIDEWAYS[4]inHow far to the right of center each sensor sits (left = negative).
SENSOR_FACE_ANGLE[4]degWhich way each sensor faces vs the robot's front: 0 = front, 90 = right, 180 = back, 270 = left.
SENSOR_SCALE[4]×Per-sensor scale fix (~1.00–1.03). Park facing a wall at known distances, read the sensor, set the scale so reading × scale = truth. V5 distance sensors read a few % high.
SIDE_PUSH_FORCENThe sideways force needed to make the wheels start sliding. Pull the chassis sideways (low, so it slides not tips) with a force gauge; record the peak before it slides. A kg luggage-scale reading converts as N = kg × 9.81.
ROBOT_WEIGHTkgThe robot's mass, on a scale. Combined with the push force: maxLateralAccel() = (F/m)·39.37 in/s² — the slip threshold the sideways noise (and boomerang) use.
Heading-convention sanity

The mounts assume LucasLib's frame: 0° = +Y (downfield), clockwise positive. The single fastest way to catch a wrong mount or angle is the map test — place the robot at a known pose and compare each sensor's expected vs. measured distance.

Things you TUNE (behaviour dials)

FieldDefaultWhat it does · which way to move it
FORWARD_NOISE0.08Predict noise along the heading, as a fraction of distance moved. Bigger = looser/jitterier but more robust; smaller = tighter but can lag.
SIDEWAYS_NOISE0.20Base sideways predict noise (larger than forward — no lateral tracker). If sideways position lags or snaps, raise it.
SLIP_GAIN0.003Extra sideways noise per unit of excess centripetal accel (s²/in). Raise if the robot loses position during hard turns.
MCL_WEIGHT0.35How hard MCL pulls chassis toward its estimate each cycle (0–1). Higher = snappier correction but jitterier; lower = smoother but laggier. 1.0 = snap straight to MCL.
ROUGHEN_STD0.4 inJitter added after resampling. Bigger = recovers from bumps faster but noisier steady state; too small = cloud collapses.
HEAVY_TAIL_FLOOR0.05Minimum per-sensor vote. Higher = more forgiving of bad readings (but mushier); lower = sharper but brittle near walls.
SENSOR_STD_FRAC0.025Sensor σ as a fraction of the reading (datasheet: ~2.5%). Larger = trust readings less (mushy); smaller = brittle to a single glitch.
SENSOR_STD_FLOOR0.5 inSmallest σ allowed (keeps close readings from being razor-peaked).
MIN_UPDATE_DIST2.0 inMove this far before weighting+resampling. Smaller = corrects more often (more CPU, risk of stationary collapse); larger = lazier.
INJECT_FRAC0.0Fraction of particles randomized each step. Off by default — it biases unobserved axes toward field-center. Raise to ~0.02 ONLY if you need to recover from being bumped/kidnapped (and accept that bias).
SEED_STD1.5 inInitial scatter around the start pose in StartMCL. Bigger if your start placement is uncertain.

Leave-alone defaults

FieldDefaultNote
NUM_PARTICLES400More = more robust on a symmetric field, but O(N) cost. 300–500 is the sweet spot; it's static constexpr (sizes the array).
FIELD_HALF70.4375 inHalf the inside field dimension. Only changes if the field does.
SENSOR_MAX_RANGE78.0 inDistance readings past this are dropped (V5 sensor goes unreliable past ~2 m).
MAX_NO_UPDATE_TIME2.0 sForce an update after this long even if nearly stationary.
DISTANCE_WEIGHT1.0Global weight on distance votes; only matters if you add other sensor types later.
TASK_DELAY_MS20mcl task loop period (~50 Hz).

Bring-up order (do not skip)

  1. Map test. Place a particle (or just the robot) at a known true pose and print, per sensor, rayToWalls(...) expected vs. the actual reading. They must agree within σ. If not, your SENSOR_* mounts or the heading convention are wrong — fix this before anything else.
  2. Scale calibration. Face each sensor at a wall at a few known distances; set SENSOR_SCALE[i] so reading×scale = truth.
  3. Slip measurement. Weigh the robot (ROBOT_WEIGHT, kg) and the sideways break-loose force (SIDE_PUSH_FORCE, N).
  4. Predict-only. Comment out the weighting; drive a known square; the cloud should follow odometry and spread. Confirms motion + conventions.
  5. Full loop, slow → fast. Watch chassis track. Tune SIDEWAYS_NOISE, then MCL_WEIGHT.
  6. Disturb it. Nudge the robot; confirm it re-converges (via roughening) and that one blocked sensor doesn't wreck it (heavy-tail).
Reminder

Everything here is validated in simulation only (see the Testing Chronicle). The numbers are sane starting points, not robot-specific truth — the measured fields especially must come from your robot.
